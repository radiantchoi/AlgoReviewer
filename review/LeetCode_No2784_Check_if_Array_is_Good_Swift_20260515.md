# 📊 코드 리뷰 보고서: LeetCode 2784. Check if Array is Good

## 1. 시간 복잡도 (Big-O 분석 및 최적화 가능성)
- **현재 코드**: `O(N)` 평균 시간 복잡도. 해시맵(`[Int: Int]`)의 삽입/조회는 평균 `O(1)`이며, 반복문 또한 최대 `N`번 실행되므로 전체 `O(N)`입니다.
- **최악 경우**: Swift의 Dictionary는 내부 해시 충돌 발생 시 `O(N)`이 될 수 있어 이론상 `O(N²)` 가능합니다. (실제 LeetCode 환경 및 정수 키 특성상 확률极低)
- **최적화 가능성**: 
  - 해시맵 오버헤드 제거: 키 범위가 명확히 `1 ~ N-1`로 제한되어 있으므로, **고정 크기 배열(`Array<Int>`)을 카운터로 사용**하면 해시 계산/충돌 처리 비용이 사라져 상수 시간 보장 및 캐시 친화성을 높일 수 있습니다.
  - 조기 반환(Early Exit): 순회 중 중복 횟수가 `2`를 초과하거나, 범위를 벗어난 숫자가 등장하면 즉시 `false` 반환하여 평균 실행 시간을 단축할 수 있습니다.

## 2. 공간 복잡도
- **현재 코드**: `O(N)` (해시맵 저장소)
- **개선 방향**: 문제의 제약 조건(`1 ≤ nums[i] < n`)을 활용하면 불필요한 동적 할당을 피할 수 있습니다.
  - **배열 기반 카운팅**: `Array(repeating: 0, count: threshold)` 사용 시 `O(N)` 공간이지만, 해시맵보다 메모리 레이아웃이 밀집되어 성능과 예측 가능성이 뛰어납니다.
  - **수학/인덱스 마킹 기법**: `O(1)` 공간으로 해결 가능한 문제입니다. (자세한 내용은 3번 항목 참조)

## 3. 보편적인 "정석" 풀이 방법
본 문제는 `"N-1까지의 정수 중 정확히 한 개가 두 번 등장하는 배열"`임을 검증하는 **Frequency/Permutation Validation** 유형입니다. 인터뷰 및 알고리즘 평가에서 선호되는 정석 접근법은 다음과 같습니다:

| 접근법 | 시간 복잡도 | 공간 복잡도 | 특징 |
|:---|:---:|:---:|:---|
| **정렬 후 인접 비교** | `O(N log N)` | `O(1)` or `O(log N)` | 구현 단순하지만 정렬 오버헤드 존재 |
| **해시/배열 카운팅** | `O(N)` | `O(N)` | 직관적, 현재 코드와 유사 |
| **인덱스 마킹** ⭐ | `O(N)` | `O(1)` | 배열을 직접 수정해 방문 여부 표시 (제약조건 만족 시 최우선) |
| **수학 공식(합)** ⭐ | `O(N)` | `O(1)` | `1~N-1` 합계와 실제 배열 합 차이를 역으로 중복값 도출 |

## 4. 현재 풀이의 적절성과 개선 가능한 부분 (엣지 케이스 포함)
- **로직 정확도**: 조건(`1~N-2는 한 번, N-1은 두 번`)을 `threshold`를 기준으로 잘 분리하여 검증했습니다. 논리적 결함은 없습니다.
- **엣지 케이스 고려**:
  - `nums.count < 2`: 문제 제약상 보통 `n ≥ 3`이지만, 방어적 프로그래밍 관점에서 예외 처리가 권장됩니다.
  - **범위 밖 입력**: `nums`에 `0`, `negative`, 또는 `≥ threshold`인 값이 들어오면 해시맵에 저장되지만, 검증 루프에서 `nil` 처리되어 `false`로 반환됩니다. 동작은 맞으나, **사전 검증**을 통해 불필요한 해시 연산을 줄일 수 있습니다.
  - **중복 초과**: 한 숫자가 `3`번 이상 등장하는 경우, 마지막 `guard`에서 `occurence == 2` 조건이 실패하여 올바르게 처리됩니다.
- **개선 제안**: 
  - 해시맵 전체 구축 후 검증하는 방식보다, `stride` 또는 `for` 루프에서 조건을 병합하여 가독성을 높이고 불필요한 변수(`number`)를 제거하는 것이 좋습니다.

## 5. Swift의 언어적 특성(Idiomatic Code) 준수 여부
- ✅ `guard let`을 활용한 조건 분리는 Swift스러운 안전성 검증 패턴입니다.
- ⚠️ **오타**: `occurences` → `occurrences` (전문성 이슈)
- ⚠️ **Dictionary 업데이트**: 
  ```swift
  // 현재 방식
  if let occurence = occurences[num] { occurences[num] = occurence + 1 } else { occurences[num] = 1 }
  
  // Swift Idiomatic 방식
  occurrences[num, default: 0] += 1
  ```
- ⚠️ **루프 스타일**: `while number < threshold` 보다 `for num in 1..<threshold` 또는 `stride(from:to:by:)` 가 Swift 컬렉션/범위 처리 관례에 더 부합합니다.
- 💡 **배열 카운팅 선호**: 정수 키 범위가 제한된 경우, `Dictionary`보다 `Array`가 Swift 런타임에서 더 효율적으로 최적화됩니다.

## 💡 종합 의견 & 개선 제안 코드
현재 풀이는 논리적으로 정확하지만, 자료구조 선택과 Swift 관례 미흡으로 인해 성능 및 가독성에서 개선 여지가 있습니다. 아래 코드는 **배열 카운팅 + Swift 관례 적용 + 조기 반환**을 반영한 버전입니다.

```swift
class Solution {
    func isGood(_ nums: [Int]) -> Bool {
        let n = nums.count
        guard n >= 3 else { return false } // 필수 엣지 케이스 처리
        
        let threshold = n - 1
        var counts = Array(repeating: 0, count: threshold) // [Int: Int] 대신 고정 배열
        
        for num in nums {
            // 1. 범위 밖 숫자 즉시 거절 (O(1) 검사로 해시 오버헤드 제거)
            guard num > 0 && num < threshold else { return false }
            
            counts[num] += 1
            // 2. 중복이 2를 초과하면 즉시 false 반환 (조기 최적화)
            if counts[num] > 2 { return false }
        }
        
        // 3. 조건 검증: 1 ~ n-2 는 정확히 1번, n-1 은 정확히 2번 등장해야 함
        return counts[0..<threshold - 1].allSatisfy { $0 == 1 } && counts[threshold - 1] == 2
    }
}
```

### 📈 개선 효과
| 항목 | 기존 코드 | 제안 코드 |
|:---|:---:|:---:|
| 시간 복잡도 (평균) | `O(N)` | `O(N)` (상수 계수 대폭 감소, 조기 반환 가능) |
| 공간 복잡도 | `O(N)` (해시맵 오버헤드 포함) | `O(N)` (밀집 배열, 캐시 효율 ↑) |
| Swift 관례 | `while`, 수동 Dictionary 업데이트 | `stride`/하위 배열 슬라이싱, `allSatisfy`, `default: 0` 패턴 |
| 유지보수성 | 조건이 루프와 분리되어 복잡 | 검증 로직이 명시적 함수로 캡슐화 |

**결론**: 알고리즘의 핵심 논리는 훌륭합니다. 다만, **정수 범위가 명확한 카운팅 문제**에서는 해시맵보다 배열 기반 접근이 Swift 생태계에서 더 권장되며, `allSatisfy`와 같은 표준 라이브러리를 활용하면 조건 검증 단계를 한 줄로 깔끔하게 정리할 수 있습니다. 인덱스 마킹이나 수학 합계 기법을 익히시면 `O(1)` 공간 솔루션도 쉽게 적용하실 수 있습니다.
